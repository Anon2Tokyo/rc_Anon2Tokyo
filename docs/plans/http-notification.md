## 需求基线
来源：仓库 `AI Coding 作业-副本.pdf`，共两页，已读取全文。

- R1：接收企业内部多个业务系统提交的外部 HTTP(S) 通知请求，尽可能可靠地投递到目标地址。
- R2：不同供应商的请求地址、Header、Body 格式不同；业务系统不需要关心外部 API 返回值。
- R3：明确系统解决和不解决的问题及理由；自行选择并说明投递语义，说明外部系统失败、长期不可用时的处理策略。
- R4：只要求最小可行实现；说明复杂度取舍及未来演进。允许使用 MQ 等中间件，但必须说明选择原因和不用它的替代方案。
- R5：交付设计说明、代码及 AI 使用说明；后者包含 AI 的帮助、未采纳的建议、用户自己的关键决策与理由。
- 原文未指定：上游接入协议、供应商查询或回调能力、成功响应判据、租户隔离级别、流量指标、重试上限。

## 用户的初始认知与架构切片
以下为用户提出的初始理解，除技术栈外，方案仍待讨论。

- 总体理解：消息中台，上游为公司多个内部系统，下游为外部供应商 HTTP(S) API；事件触发后转发通知请求。
- S1 接入：方便多个业务系统接入，考虑通过 MQ 解耦与削峰。输入为通知请求；字段、接收确认及验收方式待讨论。
- S2 隔离：因不同业务系统触发频率不同，考虑多租户与业务线隔离；具体隔离对象、程度和验收方式待讨论。
- S3 可靠投递：保证通知尽可能稳定送达；成功判据、失败处理、重复请求与最终状态待讨论。
- S4 下游差异：考虑使用策略模式屏蔽供应商差异，便于扩展；请求组装由谁负责、是否需要供应商适配待讨论。
- 用户疑问：外部供应商是否属于公司内部；如何得知对方完成通知，是否有状态查询或回调。
- 用户假设：通知流量具有突刺性。目前无流量数据，不能将此假设写成题目事实。

## Grill 决策记录

### G1：第一版的责任边界到哪里，什么算投递成功？
- 关联需求 / 切片：R1、R2、R3、R4 / S3。
- 查证依据：原文要求向目标地址投递 HTTP 通知，未要求追踪外部业务最终完成，也未承诺供应商支持查询或回调。
- 语义澄清：本服务负责调用外部 API；例如通知库存系统变更库存，不等于外部系统必须继续向某个人发送一条消息。外部系统按题目作为本服务控制范围外的依赖，不推断其具体部署或组织归属。
- 推荐方案：第一版负责接收通知任务并尝试投递；暂以 HTTP 2xx 为投递成功判据，明确这是本项目选定的约定，不证明对方业务最终完成。业务系统无需处理返回内容，但投递服务必须观察响应或异常以判断是否重试。
- 理由：供应商最终业务结果需要额外协议支持；题目没有提供这些协议。先明确可观测的成功边界，才能讨论重试与投递语义。
- 主要取舍：若供应商 2xx 响应中包含业务失败，通用 HTTP 判据无法识别；若未来要求识别，应扩展成功判据或供应商适配。超时也不能证明对方未处理，重试可能产生重复副作用。
- 用户答复：认为应按业务状态码判断外部交互结果；可靠性由消息中台负责，上游系统只需投递到 MQ。
- 决策及状态：用户未采纳仅按 HTTP 2xx 判断的初始建议，提出业务状态码方向；业务成功协议的具体定义在 G2 中继续确认。
- 需求校准：多租户、MQ、策略模式均为候选设计，原文没有要求必须采用；“多个业务系统”不自动等于完整多租户平台。“尽可能可靠”不能解释为永久不可用时也能保证送达。
- 下一步动作：通过 G2 明确供应商成功判据，通过 G3 的后续讨论划分 MQ 接收前后的可靠性责任。

### G2：业务状态码由什么协议定义？
- 关联需求 / 切片：R2、R3、R4 / S3、S4。
- 问题与依据：HTTP 状态码与响应体中的业务码是不同层次；原题没有给出供应商响应体、成功值或错误分类，不能假定各供应商统一使用 code=0。
- 推荐方案及理由：按供应商文档约定判断响应。若某供应商明确以业务码表示结果，则结合 HTTP 结果及该业务码判定；仅以 HTTP 状态表达结果的供应商使用其约定的 HTTP 成功判据。以最小供应商示例或模拟契约验证，不先设计通用规则引擎。
- 主要取舍：增加业务码判断需要具体响应协议和适配逻辑；业务码表示受理成功还是最终业务完成，也必须以协议为准，不能自行推断。
- 用户答复：OK，同意第一版定义明确标注为模拟的供应商协议，结合 HTTP 状态与响应体业务码判断结果。
- 决策及状态：已确认采用模拟协议验证；具体字段、码值及错误分类尚未确定。
- 需求校准：用户选择加强成功判定，并不与“上游不关心返回值”矛盾，因为判定由中台承担；题目没有提供真实供应商协议，模拟协议必须明确标记为设计假设。
- 下一步动作：后续定义模拟协议的成功与失败示例，明确成功表示受理还是处理完成；当前进入 G3，先确定接入责任边界。不引入通用规则引擎。

### G3：上游通过 MQ 提交后的可靠性责任
- 关联需求 / 切片：R1、R3、R4 / S1、S3。
- 用户提出的方案：内部业务系统只向 MQ 提交通知，由中台负责后续可靠投递。
- 决策及状态：已确认 MQ 接入方向及责任边界；MQ 产品、持久化与确认机制、消费确认时机、重试与失败记录尚未决策。
- 理由：用户希望上游与外部调用解耦；削峰是预期收益，实际流量仍未知。
- 必须澄清的边界：上游调用发送方法不等于 MQ 已可靠接收；上游仍需确认提交结果并处理提交失败或结果不明。业务事务完成到成功提交 MQ 之间的一致性，也不能由下游中台独自保证。
- 后续建议：以约定的持久化接收确认划分责任；中台处理接收后的投递、重试及失败留痕。具体保证依赖所选 MQ 和配置，不作无条件保证。
- 本轮推荐边界：第一版从 MQ 按约定持久化接收通知任务后开始承担投递责任；上游负责确认提交结果，处理提交失败或结果不明；本项目暂不实现各业务系统的业务事务与 MQ 发布之间的一致性。
- 取舍理由：业务事务发生在上游，中台无法恢复从未收到的业务事件；将此段明确为接入前提，可集中验证中台的投递与故障恢复。持久化消息、目标队列和发布确认等具体机制，选定 MQ 后再落实。
- 风险说明：若上游未处理业务提交后、消息发布前的崩溃，端到端仍可能漏通知；不能声称本项目已解决此类问题。发布结果不明时重发也可能造成重复，后续需讨论幂等与投递语义。
- 用户答复：进入 MQ 前由上游或 MQ SDK 处理；中台只需保证至少一次投递。
- 已确认结论：本项目不实现上游业务事务与消息发布的一致性；选择至少一次投递方向，允许重试产生重复请求，不承诺恰好一次外部业务执行。
- 补充澄清：SDK 的发送重试和确认能力不能自动覆盖所有业务事务与消息发布之间的故障窗口，具体能力取决于实现；本项目将可靠发布作为上游接入前提，不假定 SDK 已解决该问题。
- 语义限制：至少一次投递依赖故障恢复、任务保留及持续重试等条件；不能保证永久不可用的供应商最终成功。是否有限重试、失败任务如何保留及恢复仍待讨论，不能提前宣称有限重试保证至少一次成功。
- 不用 MQ 的候选替代方案：HTTP 接入并持久化任务，再由后台任务投递；后续比较运维依赖、接入方式与故障恢复复杂度，补齐 R4 要求。
- 下一步动作：先通过 G4 明确重复调用及供应商幂等的边界，再确定中台消费确认与任务恢复方案。

### G4：供应商幂等是否作为强制接入条件？
- 关联需求 / 切片：R2、R3、R4 / S3、S4；依赖 G3 已确认的至少一次投递方向。
- 具体场景：供应商已经扣减库存，但响应丢失或中台记录成功前宕机；中台重试同一任务，可能重复扣减库存。
- 推荐方案：第一版不强制所有供应商具备幂等能力；任务使用稳定标识，在供应商明确支持时，按其协议将相同幂等标识用于各次重试。模拟供应商演示支持幂等的情况。对不支持幂等的供应商，明确重复业务执行风险，不承诺消除副作用。
- 理由与取舍：题目没有保证供应商支持幂等；强制该条件会缩小可接入范围。中台本地去重可以减少已知重复任务，但无法独自消除“外部已执行、本地未知”的重复窗口。自定义一个请求头也不代表对方会去重。
- 用户答复：外部业务执行的幂等应由外部供应商保证，不应由调用方中台承担。
- 决策及状态：已确认职责边界；中台负责至少一次投递，外部业务幂等由供应商负责。此前关于强制接入条件及模拟供应商实现幂等的建议均未获采纳，不作为当前需求。
- 决策理由：副作用发生在供应商内部，调用方无法独自保证其业务只执行一次。请求标识的传递若为供应商协议所需，属于协议适配，不等于中台承担外部业务幂等实现。
- 需求校准：不得将“中台至少一次投递”扩展为“中台保证供应商恰好一次执行”；允许重复调用，并在设计中说明这个边界即可。
- 下一步动作：不继续扩展供应商幂等功能，进入 G5 明确 MQ 消费确认和任务恢复。

### G5：中台何时确认 MQ 消息已消费？
- 关联需求 / 切片：R1、R3、R4 / S1、S3；依赖 G3、G4。
- 具体问题：收到消息就 ACK，随后进程宕机且任务尚未持久化，会丢失任务；等待外部成功才 ACK，则需要由 MQ 及消费策略承担长时间失败与重投管理。
- 推荐方案：第一版将通知任务持久化到中台任务库，提交成功后 ACK MQ；后台依据持久化任务执行 HTTP 投递并记录结果、安排重试。数据库产品尚未选定。
- 推荐理由：将“接收任务”和“外部执行”分开，供应商长时间故障时，任务仍可追踪和恢复，重试进度不只保存在进程内存中。
- 代价与替代：增加任务表及后台执行逻辑；替代方案是直接消费调用外部 API，由 MQ 承担重投，但具体延迟重试与失败保留能力需结合 MQ 产品验证。
- 故障窗口：任务提交后、ACK 前宕机会导致重复消费；需以稳定任务标识避免重复入库。此处是中台接收去重，与供应商业务幂等是两个不同职责。外部成功后、本地记录成功前宕机仍可能重复调用，符合已确认的职责边界。
- 用户答复：先询问两种方案哪种更好，在比较后回复 OK，接受任务落库后 ACK、由中台管理投递重试的方案。
- 比较后的建议：在已选择 MQ 接入的前提下，推荐任务落库后 ACK。重点收益是将供应商长期失败时的任务状态、下次重试时间和恢复依据明确持久化；不是因为 MQ 自身不可靠，也不是实现至少一次必须使用数据库。
- 对 MVP 的约束：若采纳，先采用一张任务表和简单后台轮询，不引入独立调度平台；正确处理任务提交后 ACK 前的重复消费，以及重启后未完成任务的恢复。数据库持久性、任务领取与恢复逻辑同样是可靠性的必要条件，不能只靠“有表”就宣称可靠。
- 替代方案的适用条件：若已具备成熟 MQ 延迟重试、死信保留和排查工具，或只需转发和简单重试，直接消费投递可以更省组件。MQ 产品尚未选定，不将某产品机制泛化为所有 MQ 能力。
- 查证参考：RabbitMQ 官方可靠性文档将消费确认解释为责任移交，允许接收方完成持久化后确认；确认文档指出立即重新入队可能形成反复重投循环。仅用于说明方案可行性与失败机制，不代表已选定 RabbitMQ。来源：https://www.rabbitmq.com/docs/reliability 、https://www.rabbitmq.com/docs/confirms 。
- 决策及状态：已确认采用任务落库后 ACK；第一版使用一张任务表与简单后台轮询，不引入独立调度平台。产品选型及字段、领取和恢复细节待定。
- 下一步动作：通过 G6 确定长期失败任务的自动重试与保留策略，再落实故障恢复和验收场景。

### G6：供应商长期不可用时，自动重试何时停止？
- 关联需求 / 切片：R3、R4 / S3；依赖 G3 的至少一次投递方向及 G5 的任务持久化方案。
- 问题：长期失败时持续重试会占用资源；有限重试则可能在供应商恢复前停止，必须说明恢复途径，不能宣称保证最终成功。
- 推荐方案：可重试失败采用逐步增大、带上限的重试间隔；达到次数或时间上限后停止自动重试，持久化保留为待处理失败任务，记录最后失败原因，并提供最小人工重新投递入口。具体次数、间隔和入口形式另行确定。
- 理由与取舍：避免长期故障持续消耗投递资源，保留排查和恢复依据；代价是上限之后需要人工介入，无法无条件承诺至少一次成功送达。
- 语义说明：允许重复尝试、故障后可恢复，不等于每个任务必定成功；G3 的至少一次投递在采用有限重试时须明确此限制。供应商明确拒绝且原请求不变就无法成功的错误，后续按协议分类，不默认全部反复重试。
- 替代方案：对可重试失败持续自动重试、间隔增长至上限后保持低频；适合明确要求恢复后无需人工继续投递的场景，但要承担积压、过期任务及容量管理成本。
- 用户答复：选择“有限重试＋失败保留＋人工重投”。
- 决策及状态：已确认。第一版包含有限自动重试、持久化失败任务与最小人工重投能力；具体次数、间隔、错误分类和入口形式待细化，不自动扩展为管理后台。
- 已确认取舍：控制自动重试的资源消耗，保留失败原因和恢复途径；达到上限后依赖人工介入，不承诺所有任务最终成功。
- 下一步动作：先通过 G7 确定请求组装职责，随后结合供应商协议确定可重试错误、次数及间隔，并细化人工重投流程。

### G7：上游提交完整 HTTP 请求，还是由中台组装供应商请求？
- 关联需求 / 切片：R1、R2、R4 / S1、S4。
- 问题与依据：原题说接收业务系统提交的外部 HTTP 通知请求，并指出供应商地址、Header、Body 不同；没有要求中台理解各业务事件。用户初步提出策略模式屏蔽供应商细节，尚未确定是请求组装还是响应判定的适配。
- 推荐方案：第一版上游提交稳定请求标识、业务系统标识、供应商标识，以及目标 URL、HTTP 方法、Header、Body；中台负责可靠投递，并按供应商协议判定响应。示意字段不等于已确认接口，具体约束和配置归属后续确定。
- 理由与取舍：最贴近原题“提交外部 HTTP 通知请求”，避免中台同时承担注册、支付、库存等业务事件到供应商请求的映射；代价是上游仍需了解供应商请求格式，不能声称完全屏蔽供应商细节。
- 替代方案：上游提交供应商标识、操作类型和业务参数，中台适配器负责 URL、Header、Body 组装及结果判定；能屏蔽更多供应商细节，但扩大中台职责和新增供应商时的开发范围。
- 需求校准：策略模式不是既定实现要求；若只需响应判定适配，不顺势扩展请求模板系统或通用规则引擎。供应商鉴权信息的配置归属也需随接口边界落实。
- 用户答复：选择 B，由中台组装供应商请求。
- 决策及状态：已确认。上游提交供应商标识、操作类型、业务参数及必要任务标识；中台负责按供应商协议组装 URL、Method、Header、Body，并判定响应。具体字段与鉴权配置归属待细化。
- 决策理由与取舍：沿用用户最初希望屏蔽供应商细节的目标，接受中台维护供应商请求映射的成本；未采纳 agent 推荐的 A（上游组装完整 HTTP 请求）。用户没有额外陈述选择理由，不扩写为用户原话。

### G8：第一版业务系统隔离需要达到什么程度？
- 关联需求 / 切片：R1、R4 / S2；用户初始理由是不同业务系统触发频率不同。
- 问题：仅在任务中记录业务系统标识，可以区分来源，但无法防止高流量业务占满投递资源；独立部署或独立数据库成本更高，也不是原题要求。
- 推荐方案：第一版使用共享 MQ 和数据库，任务记录业务系统标识；在投递调度中按业务系统轮流取任务，并设置每个业务系统的在途投递上限。该方案提供投递阶段的基本公平性和资源限制，不宣称全链路或物理隔离。
- 理由与取舍：对应用户提出的频率差异，控制一个业务系统对其他业务的挤占；增加调度与并发限制代码，共享接入、数据库及总执行容量仍可能形成瓶颈。可行参数及执行模型待后续确认。
- 可选范围：A 仅标记业务来源，暂不做资源隔离；B 共享基础设施并实现投递阶段公平调度与每业务并发限制；C 按业务使用独立队列和独立消费/投递资源，进一步说明共享或独立存储的边界。
- 需求校准：业务来源标识、资源隔离和数据访问权限是不同问题。此轮只确定资源隔离范围；不把业务标识字段等同于完整多租户或数据权限隔离。
- 用户答复：先询问 C 的复杂性；在明确共享基础设施、按业务分配独立队列与消费及投递资源的范围后，回复“是的”，确认采用该范围。
- 补充比较：C 不等于每个业务独立部署整套系统。有限且预先配置的业务系统可共享 MQ 实例、应用和数据库，但各用独立队列、消费并发和固定容量的投递执行器；复杂度中等，职责比共享线程池内实现公平调度更直观，不能笼统断言比 B 更复杂。
- 关键约束：G5 已选择落库后 ACK，因此仅拆 MQ 队列只能隔离接入；落库后的任务扫描和投递也要按业务分开，各业务限制取任务数量并使用独立且有界的投递资源，否则仍会被统一调度淹没。避免先全表取一批任务再按业务分类，因为大业务仍可能占满该批次。
- 成本与限制：队列、消费者、执行器及其参数随业务数量增长；还要约束共享 HTTP/数据库连接资源。共享进程、数据库、MQ 节点和供应商仍是共同故障或容量边界，不保证完全故障隔离。动态租户创建、资源自动分配、独立部署与独立数据库会进一步显著增加复杂度。
- 调整后的建议：如果当前优先目标是让少量固定业务的资源归属直观，可以选择共享基础设施下的 C，不必坚持 B；第一版不做动态租户管理。这里是方案解释和条件建议，尚未获得用户选择。
- 决策及状态：已确认采用 C：共享 MQ、数据库和应用，每业务独立队列、消费并发和有界投递线程池；按业务分别取到期任务。业务预先配置，不实现动态租户管理或每业务独立部署。
- 决策理由与取舍：采用讨论中资源归属直观、投递资源隔离清晰的方案；接受每业务维护队列和执行资源的成本，同时明确共享基础设施仍可能产生相互影响。
- 下一步动作：在实现方案中落实每业务资源上限及独立任务扫描；用 A 业务积压或慢响应时 B 仍能投递的场景验证投递资源隔离。通过 G9 确定模拟供应商范围，再细化技术选型和运行模型。

### G9：第一版用多少个模拟供应商验证适配？

### G10：第一版应用按单实例还是多实例运行？
- 关联需求 / 切片：R3、R4 / S2、S3；依赖 G5 任务库与后台扫描、G8 每业务独立投递资源。
- 推荐方案：第一版按一个应用实例运行，验证进程重启后的未完成任务恢复；MQ 和数据库持久保存数据，不使用进程内状态作为任务唯一依据。暂不提供应用高可用或水平扩容。
- 理由与取舍：单实例便于保持扫描、任务执行及按业务分配资源的逻辑直接，适合作业 MVP；应用停机期间暂停投递，重启后恢复。单实例仍须防止本进程扫描重叠或重复提交同一在途任务，并处理执行中崩溃的恢复，不等于不需要任务领取与状态管理。
- 多实例替代：若第一版要求多应用实例并行，需要任务的原子领取、领取超时或租约、旧执行者结果写入约束，并明确每业务并发限制是每实例还是全局。允许重复 HTTP 调用不代表可以忽略任务状态竞争或积压控制。
- 与 G8 的关系：多个业务各自有独立执行资源，不要求每个业务运行在独立进程；共享单实例的故障会影响所有业务，符合此前明确的基础设施共享边界。
- 用户答复：单实例运行，支持重启恢复任务即可。
- 决策及状态：已确认单实例及重启恢复，不实现多实例高可用或分布式调度。
- 决策理由与动作：将第一版范围限定在已持久化任务的进程故障恢复；实现前明确待执行、等待重试、执行中及失败任务的恢复行为。失败待人工处理的任务不能在重启时被无条件恢复为自动重试。
- 验收方向：任务落库后 ACK 前宕机、ACK 后执行前宕机、HTTP 调用中宕机、外部成功但本地未记录时宕机，以及重启后重试预算不被无故清零。具体测试方式在实现推导中落实。
- 下一步动作：通过 G11 确定 MQ/数据库产品，再整理任务状态与故障恢复方案。

### G11：MQ 和任务数据库采用什么产品？

- 理由与取舍：RabbitMQ 的队列与手动确认适合已选的按业务队列、落库后 ACK 流程；MySQL 事务可支撑任务提交、状态更新及唯一约束。代价是本地需运行两个基础设施服务，不因采用产品就自动宣称具备高可用。

- 查证依据：RabbitMQ https://www.rabbitmq.com/docs/reliability 、https://www.rabbitmq.com/docs/confirms ；MySQL https://dev.mysql.com/doc/refman/8.4/en/innodb-autocommit-commit-rollback.html 。数据库提交持久性和 MQ 确认语义均依赖正确配置。
- 本地只读检查：PATH 中存在 Java（路径指向 JDK 17.0.8）、Maven、Docker 命令；尚未检查实际版本、Docker 服务状态或已有中间件实例。仓库尚无构建或 Compose 配置。
- 用户答复：将 RabbitMQ 替换为 RocketMQ；按仅替换 MQ 的指示，数据库沿用 MySQL。
- 决策及状态：已确认 RocketMQ + MySQL。此前 RabbitMQ 推荐保留为历史建议，不是当前选型；用户未说明替换原因，不虚构其偏好依据。未安装、启动服务或生成业务代码，具体版本与 SDK 待实现前核对。
- 对 G5 的适配：落库提交成功后才报告消费成功。RocketMQ PushConsumer 在监听器内完成持久化后返回成功，不能先把持久化工作交给异步线程就返回成功；若采用 SimpleConsumer，则持久化后显式 ACK。具体 SDK 类型后续确定，不照搬 RabbitMQ basicAck API。

### G12：HTTP 投递失败如何分类，自动尝试多少次？
- 关联需求 / 切片：R3、R4 / S3；依赖 G2、G6、G9。
- 推荐规则：网络异常、超时、HTTP 408/429/5xx 和模拟供应商明确表示暂时失败的业务码进入有限重试；其余明确的 HTTP 4xx 或不可恢复业务错误保留为失败，等待人工处理；无法解析响应或未知业务码有限重试，耗尽后保留失败，不误判成功。真实供应商接入时以其协议覆盖分类。
- 推荐预算：每轮最多尝试 5 次，包含首次请求；四次重试间隔依次为 10 秒、30 秒、2 分钟、10 分钟，参数可配置。为 MVP 的明确示例值，不声称来源于实际 SLA；测试使用更短间隔。
- 理由与取舍：避免永久拒绝被无意义地反复调用，给临时故障恢复机会，同时控制自动重试资源。耗尽后进入失败待人工重投，符合 G6。
- 边界：该预算针对 HTTP 投递，不复用 RocketMQ 的消费重试次数。崩溃恢复不清零已记录预算；人工重投是否开启新一轮及保留哪些历史信息，后续明确。
- 用户答复：接受。
- 决策及状态：已确认上述失败分类和默认预算：每轮最多尝试 5 次（含首次），四次间隔为 10 秒、30 秒、2 分钟、10 分钟，支持配置；测试可缩短间隔。
- 决策理由与动作：按已接受方案区分临时失败与明确不可恢复错误，控制自动尝试次数；将分类、间隔和预算落实到任务状态流转与验收场景。未知响应不视为成功，真实供应商按其协议调整。

### G13：人工重投怎样操作，是否开启新的尝试预算？
- 关联需求 / 切片：R3、R4 / S3；依赖 G6 失败保留、G10 重启恢复及 G12 重试预算。
- 推荐方案：提供内部运维 HTTP 接口，按业务系统与任务标识查询任务，并仅对失败状态的任务发起重投；无需管理页面。重投沿用原任务标识和业务参数，开启新一轮最多 5 次尝试。
- 理由与取舍：运维能先查看原因，处理供应商故障或中台配置问题后，再明确恢复任务；一张任务表即可记录当前轮次、当前轮尝试数、累计尝试数和最近失败信息。不扩展完整审计系统或逐次请求历史表，但不能声称保存了全部历史。
- 状态约束：重投通过条件更新将失败任务改为待执行，只有一次更新可成功，避免重复点击同时开启多轮；成功或正在处理的任务不允许重投。保留累计尝试数并增加人工重投次数，当前轮次数归零。
- 参数约束：该入口不修改原业务参数；若参数本身错误，上游修正后使用新请求标识提交新任务。人工重投接口的访问控制与业务来源边界在最终设计中明确，不作为对上游开放的新业务提交接口。
- 重启区别：进程重启不会开启新一轮或增加预算；失败任务仍等待人工处理，只有显式人工重投才能重置当前轮预算。
- 用户答复：接受。
- 决策及状态：已确认内部运维接口查询及重投失败任务，原参数不变，开启新一轮预算并保留累计次数；不做管理页面。
- 决策理由与动作：区分显式人工恢复与自动重启恢复，避免无限增加自动预算；落实失败状态条件更新、重复点击保护和累计次数保留。

- 本轮待确认：用户是否接受上述责任边界，将版本防旧覆盖留为扩展；目前未新增版本字段或模拟供应商版本控制功能到已确认范围。

- 顺序边界修正：不新增时间戳或版本控制到第一版；原有至少一次投递、并发执行和失败重试可能改变完成顺序。仅要求上游按序发送不能推出端到端顺序保证，幂等也不能解决不同事件的顺序问题。当前方案继续不承诺端到端有序；若业务依赖最终顺序，须另行明确设计。

### G15：当前队列按业务方划分，还是按供应商和操作划分？
- 关联需求 / 切片：R1、R2、R4 / S2、S4；回顾 G8、G11，不擅自替换已确认方案。
- 用户问题：一个业务方一个队列，还是一个外部供应商操作类型一个队列？
- 当前已确认模型：按业务方设置独立 Topic、Consumer Group、消费及 HTTP 投递资源。此处“每业务一个队列”是逻辑接入通道的简写，不意味着 RocketMQ Topic 只能有一个内部 MessageQueue。具体队列数量待运行配置确定。
- 数据流：业务 A 的 Topic 可以包含供应商 X/Y 的多种操作；消费后统一写任务库，按业务 A 的独立投递资源执行，再依据 supplier/operation 选择适配器。第一版实际只支持更新客户状态这一操作。
- 按业务方划分的收益与限制：直接满足已确认的业务资源隔离，高流量业务 A 不占用业务 B 的专属投递线程；同一业务内，慢供应商仍可能占用该业务的投递线程，不能宣称已经实现供应商故障隔离。
- 按供应商/操作划分的收益与限制：配合对应的独立投递资源，可将慢供应商或特定操作限制在其资源内，也便于按目标 API 限速；但多个业务共用同一供应商通道时，大业务仍可能挤占小业务，不能替代已确认的业务隔离。
- 关键依据：任务落库后已确认 MQ 消费，实际 HTTP 隔离由任务调度及投递执行资源决定；仅改 Topic 拆分而不改落库后调度，不能获得期望的供应商隔离或顺序保证。
- 建议：当前保留按业务方接入及投递资源划分，供应商和操作作为任务路由字段；若用户关心供应商故障或配额，可另加按供应商/操作的并发或速率约束，不必立即创建业务×供应商×操作的全组合队列和线程池。
- 用户澄清：只是好奇模型的区别，不是在提出慢供应商隔离需求或调整队列模型。
- 决策及状态：保留 G8/G11 的按业务方划分方案；供应商/操作维度仅作为比较说明，不新增供应商级调度、限流或队列要求。

## 收敛设计（G14 已授权执行）

### 主链路与消息契约

```text
内部业务 → 对应 RocketMQ Topic → 独立消费者 → MySQL 任务提交 → 返回消费成功
                                                   ↓
                                    按业务扫描 → 独立有界投递线程池
                                                   ↓
                                    供应商适配器 → HTTP → 更新任务结果
```

演示预配置 business-a、business-b 两个业务来源；每个来源可调用 supplier-a 或 supplier-b，不固定一对一映射。

```json
{
  "requestId": "contact-update-001",
  "supplier": "supplier-a",
  "operation": "UPDATE_CONTACT_STATUS",
  "payload": { "contactId": "c-001", "status": "ACTIVE" }
}
```

- 业务来源由消费者订阅的 Topic 配置确定，不信任消息自行声明的业务归属。示例发布端负责可靠发送，MQ 权限配置决定实际发布访问边界。
- `(businessId, requestId)` 唯一标识一次通知任务；requestId 由上游生成，并在重发时保持不变。同标识同内容重复接收不重建任务，同标识不同内容不覆盖原任务，记录冲突并进入 MQ 接入异常处理。
- 上游不提供 URL 或鉴权 Header；供应商地址和凭据由中台配置，凭据不放入示例消息或任务查询结果。
- status 仅接受 ACTIVE/INACTIVE；A 映射为 contactId/status，B 映射为 user_id/enabled（true/false）。两个 POST 接口采用不同路径和 Header。
- 模拟 A 的 code=0、B 的 result=SUCCESS 配合 HTTP 2xx 表示本次调用成功；暂时失败示例分别为 code=1001、result=TEMPORARY_FAILURE，不可恢复示例分别为 code=2001、result=INVALID_ARGUMENT。不是任何真实供应商的协议。
- 不自动跟随 HTTP 重定向；非预期状态或响应使用有限重试，明确的不可恢复错误进入失败状态。HTTP 调用必须有有限超时，具体配置写入运行说明。

### 状态和预算

采用五种任务状态：PENDING（待执行）、PROCESSING（执行中）、RETRY_WAIT（等待重试）、SUCCEEDED（成功）、FAILED（等待人工处理）。

```text
PENDING / 到期 RETRY_WAIT → PROCESSING → SUCCEEDED
                                    → RETRY_WAIT（可重试且未耗尽）
                                    → FAILED（不可恢复或预算耗尽）
FAILED → 人工重投 → PENDING（新一轮）
```

- 一张任务表保存业务/请求标识、供应商、操作、业务参数、状态、本轮与累计尝试数、人工重投次数、下次执行时间、最近失败原因及时间戳；唯一索引防止重复建任务，业务/状态/时间索引用于扫描。
- 按业务执行器的空闲容量取任务；在工作线程实际开始处理时，条件更新状态为 PROCESSING 并增加尝试数，事务提交后才发 HTTP。HTTP 期间不持有数据库事务。
- 防止单实例扫描重复提交同一任务；线程池满时不无限堆积，不把尚未执行的任务提前记为 PROCESSING。
- 预算统计为已开始且持久化登记的尝试。登记后、HTTP 发出前宕机也占一次预算，因为恢复时无法可靠判断请求是否发出；不会因此无上限自动增加尝试。
- 成功后保留最后一次失败信息供排查，当前状态以 SUCCEEDED 为准；只记录最近失败，不宣称有完整逐次执行历史。
- 结果写库失败时不得直接再次调用 HTTP；保留 PROCESSING 并尝试完成结果持久化，持续失败则停止相关工作并报告，依靠受控重启恢复，避免已领取任务静默卡死。

### 单实例启动恢复

恢复在消费者和投递扫描启动前完成，前提是旧实例已退出，不支持两个实例同时操作任务库。

| 原状态 | 重启行为 |
| --- | --- |
| PENDING | 保留，正常调度 |
| RETRY_WAIT | 保留原预算及下次执行时间，到期才执行 |
| PROCESSING，预算未耗尽 | 记录执行结果未知，转为 RETRY_WAIT，按本轮次数安排下一次间隔 |
| PROCESSING，预算已耗尽 | 转为 FAILED，标注结果未知，等待人工处理 |
| SUCCEEDED / FAILED | 保留，不自动重投 |

外部已成功而结果尚未记录时可能再次调用，由供应商承担外部业务幂等；这个窗口不承诺消除。

### 接入异常和人工入口

- DB 写入失败不报告 MQ 消费成功；数据库事务提交后才返回成功。RocketMQ 消费重试耗尽后的死信保留与恢复命令写入 README，单独验证，不能假定死信永不过期。
- 无法解析、缺少标识、未知供应商或同标识异内容等不能成为合法任务的消息，走 RocketMQ 失败/死信路径；保留原消息并提供修正后重发方法，不以只打印日志后返回成功代替处理。
- 建议接口：`GET /internal/tasks/{businessId}/{requestId}` 查询、`POST /internal/tasks/{businessId}/{requestId}/retry` 重投。
- 运维接口仅面向本地/内部管理员，使用配置的运维令牌保护；不做每业务用户权限系统。未知任务返回 404，非失败状态重投返回 409；并发重投用条件更新保证一次状态转换。
- 重投增加人工重投次数，本轮尝试数归零，累计次数和最近失败原因保留，参数及标识保持不变。错误业务参数需上游提交新任务。

### 明确不做及保证限制

- 不实现上游事务消息一致性、供应商业务幂等、动态租户管理、独立基础设施、完整审计后台、多实例高可用和跨任务顺序保证。
- 至少一次是允许重复的投递方向，受有限预算和人工恢复约束；不保证永久故障下最终成功，不把响应成功解释为未约定的后续业务流程完成。
- 共享数据库、Broker 和应用仍可能影响所有业务；独立执行资源仅用于控制接入和投递阶段的相互挤占。

### 验收清单

1. 两个业务来源可分别调用两个供应商，验证请求映射和不同响应解析，防止写死业务与供应商对应关系。
2. 同业务同请求重复消费只有一条任务，同标识异内容不能覆盖原任务。
3. DB 提交前失败不会确认 MQ；提交后确认前崩溃导致重投时不重复建任务。
4. 临时失败按间隔重试，第 5 次失败进入 FAILED；不可恢复失败直接进入 FAILED；未知或不可解析响应不能标成功。
5. 重启恢复覆盖上述五类状态，次数和待重试时间不被重置。
6. 人工重投仅允许失败任务，开启一轮预算并保留累计信息；并发重复操作不会同时生成多轮。
7. A 业务积压或 HTTP 缓慢时，B 仍可通过自己的接入和投递资源完成任务，不将共享设施极限外推为完全隔离。
8. 非法消息和持续落库失败的 MQ 死信有可操作的恢复说明；运维接口缺少令牌时拒绝操作。
